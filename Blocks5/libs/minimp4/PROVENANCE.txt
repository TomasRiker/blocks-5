minimp4
=======

MP4 muxer, single header, public domain. Writes the container for recorded
gameplay; see src/videorecorder.cpp.

  https://github.com/lieff/minimp4   commit 5a212a18dba7dca09543bbc7d65619274fd2931a
  CC0 1.0 Universal (LICENSE)

minimp4.h is byte-identical to upstream, CRLF line endings and all. Do not edit
it - see below for why it does not need editing.

minimp4_impl.c is not upstream: it is the one translation unit that instantiates
the header, and the place where the library is bent into shape. It has to stay
separate from minih264's, because both headers define a bitstream struct called
bs_t inside their implementation halves and the two collide if both are
instantiated in one file.

THE PROBLEM
-----------
minimp4 writes the 'esds' descriptor of an audio track with the
objectTypeIndication byte hardcoded to AAC, ignoring the
object_type_indication field the caller filled into MP4E_track_t. That byte is
the only thing that tells a demuxer whether an 'mp4a' track holds AAC or MP3 -
Microsoft's documentation for the MPEG-4 File Source lists that one sample entry
as meaning "AAC or MP3". So upstream can mux AAC and nothing else: an MP3 track
comes back out declared as AAC and does not decode.

It also writes the descriptor only when a decoder-specific info blob has been
set with MP4E_set_dsi, which AAC has and MP3 does not.

HOW IT IS SOLVED WITHOUT PATCHING
---------------------------------
The constant is a macro, and minimp4's declarations and its implementation sit
on opposite sides of its include guard in the same file - "#endif //MINIMP4_H"
at line 509, the MINIMP4_IMPLEMENTATION block at 511. So minimp4_impl.c includes
the header twice: once for the declarations, which is what defines the macro,
then redefines the macro to read the caller's field, then includes it again for
the implementation. Upstream uses the macro in exactly one place, which is the
one that needs changing.

The missing descriptor is the caller's problem, and videorecorder.cpp solves it
by calling MP4E_set_dsi(mux, track, "", 0). A zero-length blob is enough to make
the descriptor appear.

DETECTING THAT IT STILL WORKS AFTER AN UPGRADE
----------------------------------------------
Three layers, because no single one covers everything. All were tested by
deliberately breaking a copy of the library:

  macro removed or renamed  -> #error at compile time
  macro no longer 0x40      -> #error at compile time
  macro used where `tr` is
    not in scope            -> ordinary compile error, since the replacement
                               dereferences it
  macro no longer used at
    that site               -> NOT visible to the preprocessor. A counter in
                               minimp4_impl.c is bumped on every expansion, and
                               videorecorder.cpp checks it moved while closing a
                               file that has an audio track, logging a loud
                               error if it did not.

THE DESCRIPTOR IS TIDIED UP AFTERWARDS
--------------------------------------
The macro override gets the one byte that decides whether the file plays at all.
What it cannot reach is the rest of what upstream writes, which is not
conformant: the reserved low bit of the stream-type byte is left clear, there is
no SLConfigDescriptor, and forcing the descriptor to appear at all leaves a
DecoderSpecificInfo that MP3 must not have. None of that is reachable by macro -
the stream-type byte is a literal, the SLConfigDescriptor would have to be a
sibling of a descriptor whose length is computed from the caller's data, and
"descriptor present" and "DSI present" are the same condition in upstream's
code.

So videorecorder.cpp fixes it in the finished file instead, in
makeAudioDescriptorConformant(). The trick that makes this safe is the DSI
length: videorecorder.cpp passes exactly ONE byte, not zero, and at that length
upstream's descriptor comes out 23 bytes long - exactly the length of a
conformant one. The replacement is therefore done in place and not a single box
size changes anywhere in the file.

  upstream + override:  03 15 00 00 00 04 10 6b 14 00 06 00 <max:4> <avg:4> 05 01 XX
  rewritten:            03 15 00 00 00 04 0d 6b 15 00 06 00 <max:4> <avg:4> 06 01 02
  ffmpeg, for comparison:
       03 80 80 80 1b 00 01 00 04 80 80 80 0d 6b 15 00 00 00 00 01 f7 12
       00 01 f7 12 06 80 80 80 01 02

The rewritten form and ffmpeg's are structurally the same descriptor. They still
differ in three ways, all legal and all informational: ffmpeg encodes the
descriptor lengths in the four-byte 0x80 0x80 0x80 form rather than the compact
one, its ES_ID is 1 rather than 0, and its bufferSizeDB is 0 where minimp4
computes one.

The rewrite verifies the exact 23-byte pattern before touching anything and
refuses if it does not match, so a future minimp4 that lays the descriptor out
differently leaves the file alone rather than corrupting it - and the file still
plays, because the macro override has already put the right codec byte in it.
That is the reason both mechanisms exist: the override is what makes the file
work, the rewrite is only polish.

A NOTE ON FRAGMENTS
-------------------
MP4E_open takes a "fragmented" flag. Leave it off. Microsoft's MPEG-4 File
Source documents 'moof' boxes as unsupported before Windows 8.
