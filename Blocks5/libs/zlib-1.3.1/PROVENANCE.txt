zlib 1.3.1 (with contrib/minizip)
=================================

DEFLATE, plus Gilles Vollant's minizip on top of it. This is what makes the
virtual filesystem work: FileSystem::openFile serves a member of a zip archive
as readily as a real file (src/file_archived.cpp), and the campaign editor
writes archives back out (src/gs_campaigneditor.cpp). The game cannot start
without it - data.zip is where every asset lives.

  https://github.com/madler/zlib   tag v1.3.1
  zlib licence, in the header comment of zlib.h; minizip carries its own
  Info-ZIP-derived notice at the top of unzip.c and zip.c

TWO LOCAL CHANGES, BOTH ONE LINE
--------------------------------
Every file here was compared against the tag above. All 37 are byte-identical
except these two, and in both cases the change is a comment marker:

  contrib/minizip/unzip.c:72     //        #define NOUNCRYPT

Upstream defines NOUNCRYPT, which compiles the decryption support out of unzip.c
entirely. The game's archives are password-protected - that is the whole point
of the archive.zip<password>/file and archive.zip[encrypted]/file syntax in
FileSystem - so with the upstream default nothing in data.zip can be read and
the game does not start. This is load-bearing; do not "restore" it on an update.

  contrib/minizip/iowin32.c:37   //#define IOWIN32_USING_WINRT_API 1

Upstream turns on the WinRT file API when WINAPI_FAMILY says the target is a
Store app rather than a desktop one. This is a desktop Win32 build; the branch
should never be taken, and commenting the define out means it cannot be taken by
accident if the Windows SDK headers change their mind about the family macros.

WHAT IS COMPILED
----------------
Both builds compile the same eleven core files - adler32, compress, crc32,
deflate, infback, inffast, inflate, inftrees, trees, uncompr, zutil - and from
contrib/minizip: ioapi.c, unzip.c, zip.c. The Visual Studio build adds
iowin32.c; the Emscripten build does not, because it is Win32-only.

Vendored but deliberately not compiled:

  gzclose.c gzlib.c gzread.c gzwrite.c   the gz* stdio wrapper layer, unused -
                                         everything goes through minizip
  contrib/minizip/mztools.c              a repair tool for damaged archives

They are kept so the directory is a complete, recognisable zlib rather than a
subset someone has to reverse-engineer.

UPDATING
--------
Drop in a new release, then re-apply the two lines above - they are the only
thing to carry forward. Check contrib/minizip separately: it is barely
maintained upstream and has changed shape between releases before.
